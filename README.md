# intent-to-action — Behavior Cloning on Meta-World Manipulation Tasks

[![Eval CI](https://github.com/kashishsood/intent-to-action/actions/workflows/eval_ci.yml/badge.svg)](https://github.com/kashishsood/intent-to-action/actions/workflows/eval_ci.yml)

## Key Finding

**Step-wise prediction accuracy does not predict closed-loop task success.**
`pick-place-v3` had the second-lowest offline MAE (0.024) of all five tasks — placing it in the best half by imitation accuracy — yet the worst closed-loop success rate (16%).
Three tasks with substantially higher MAE achieved 100% success.

| Task | Step-wise MAE | Step-wise MSE | Task Success |
|:---|:---:|:---:|:---:|
| `reach-v3` | 0.0182 | 0.00340 | **58.0%** |
| `pick-place-v3` | **0.0240** | 0.00934 | **16.0%** ← flagged |
| `door-open-v3` | 0.2943 | 0.45446 | 100.0% |
| `drawer-open-v3` | 0.1392 | 0.08916 | 100.0% |
| `button-press-topdown-v3` | 0.1717 | 1.06559 | 100.0% |
| **Overall** | **0.1295** | **0.32439** | **74.8%** |

*50 closed-loop rollouts per task (250 total), model checkpoint `models/best_bc_model.pt`, CPU, 2026-09-12.*

The most plausible explanation — consistent with the data but not definitively isolated —
is that tasks requiring precise contact (grasp, placement) are more sensitive to
compounding positional drift under single-step Markovian BC than tasks where physical
constraints (door hinge, button surface) funnel the robot toward the goal regardless of
small action errors. Other factors cannot be ruled out: insufficient demonstration
coverage near contact configurations, or the inherent difficulty of the grasp sub-task
relative to 50 training episodes. See [`eval_report.md`](eval_report.md) for the full
flagged-gaps analysis.

## What this project does

A self-contained pipeline for:

1. **Data collection** (`collect_demonstrations.py`) — runs five built-in Meta-World
   scripted oracle policies for 50 episodes each; records observations, actions, and
   per-timestep success flags; splits by episode (70/15/15) into Parquet files.

2. **Imitation learning** (`train_bc.py`) — trains a three-layer MLP (256 hidden units)
   via supervised regression on the demonstration data. Inputs are normalised with
   per-feature mean/std from the training split. Best validation checkpoint saved to
   `models/best_bc_model.pt`.

3. **Evaluation** (`eval_harness.py`) — computes step-wise MAE/MSE on the held-out test
   split and runs closed-loop rollouts in live simulation. Writes
   [`eval_report.md`](eval_report.md) with a unified comparison table and a
   flagged-gaps section.

4. **CI quality gate** (`.github/workflows/eval_ci.yml`) — nightly job fails the build
   if any task's success rate drops more than 10 percentage points below the baseline
   in [`eval_baseline.json`](eval_baseline.json). Per-PR runs execute only a fast smoke
   test (imports, baseline schema, dataset columns; < 2 min).

## Why Meta-World instead of real demonstration data

Collecting real robot manipulation demonstrations requires physical hardware and operator
time. This project uses Meta-World's MT10 benchmark as a controlled substitute for the
following reasons:

- **Scripted oracle policies**: Meta-World ships hand-authored closed-form controllers
  for every task, giving high-quality, reproducible demonstrations without teleoperation.
- **Standardised observation space**: all five tasks share a 39-dimensional observation
  vector (end-effector position, object pose, goal position, joint state) and a
  4-dimensional action space (Δx, Δy, Δz, gripper).
- **Binary success criterion**: each task has a well-defined `info['success']` flag,
  making success rates directly comparable across methods without subjective labelling.
- **Headless rendering**: MuJoCo supports EGL rendering, allowing CI pipelines to run on
  standard cloud VMs without physical displays or GPUs.

The scripted policies exploit privileged simulator state and are not learned. A BC model
trained on their demonstrations therefore operates under covariate shift: it observes the
same state space but must generalise to distributions not covered by the oracle's
deterministic trajectories.

## Quickstart

```bash
pip install -r requirements.txt

# 1. Collect demonstrations (~10 min on CPU)
python collect_demonstrations.py

# 2. Train BC policy (~20–30 min on CPU)
python train_bc.py

# 3. Evaluate: offline metrics + 250 closed-loop rollouts (~15–20 min on CPU)
python eval_harness.py \
    --model-path models/best_bc_model.pt \
    --test-file  dataset/test.parquet \
    --episodes-per-task 50 \
    --output-report eval_report.md

# Optional: pick-place trajectory diagnostics
python diagnose_pick_place.py
```

## CI quality gate

The nightly `eval / quality-gate` job (`.github/workflows/eval_ci.yml`) fails if any
task's closed-loop success rate drops more than **10 percentage points** below the
stored baseline. To make it block merges:

1. Push this repo to GitHub and trigger a manual run from the Actions tab so the check
   name registers.
2. **Repo Settings → Branches → Branch protection → main → Require status checks →**
   add `eval / quality-gate`.

To raise the baseline intentionally after a model improvement, edit
`eval_baseline.json` and commit it alongside the new checkpoint.

> **Note on CI verification**: the nightly job requires `models/best_bc_model.pt` to
> be present in the repo (either committed directly or restored from a GitHub Release
> artifact). Large model files should use [Git LFS](https://git-lfs.github.com/) or a
> separate artifact store. Committing a 1.3 MB checkpoint directly is acceptable for a
> project of this scale; files above ~50 MB should use LFS.
